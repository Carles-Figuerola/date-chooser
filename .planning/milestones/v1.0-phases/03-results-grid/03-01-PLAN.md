<objective>
**As a** person holding a Date Chooser poll link, **I want to** see, below the voting form, a
grid of who answered Yes/No/Maybe for each slot with per-slot tallies and the best slot(s)
highlighted, plus everyone's comments, **so that** I can tell at a glance which slot works best
for the group.

This plan is the phase's tracer + data-completeness slice for the **participant route only**
(`GET /poll/{ptoken}`). It wires a new read-only aggregation query through a new view-model +
ranking helper, a new shared `results.html` partial, and the existing `handleVoteForm`, proven
end-to-end with a real multi-participant HTTP test. Admin-route parity (ADM-01) and the grid's
visual CSS are Plan 03-02.

Purpose: deliver the core RES-01..04 behaviors as one demoable vertical slice on the participant
page, proving the store→view→partial architecture before extending it to the second route.
Output: `internal/store/results.go` (+test), a `buildResultsGridView`/`rankBestSlots` helper pair,
`internal/web/templates/results.html`, and grid + comments rendering on `GET /poll/{ptoken}`.

Reversibility: every change here is read-only aggregation over existing tables and additive
template/handler wiring — fully reversible, no schema change, no data migration, no one-way door.

Scope notes recorded as visible choices (per planning context):

  SPEC.md exists for Phase 3. Edge cases are instead covered via CONTEXT.md decisions and
  UI-SPEC's `## UI Considerations` section, lifted into `must_haves.truths` above.
- No new identity model this phase — purely read/aggregate over Phase 2's existing
  participants/responses; no assumption-delta checkpoint applies.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| participant → server (stored data) | Display names and comments were submitted by untrusted participants in Phase 2 and are now rendered back into the results grid/comments for every other viewer (stored-XSS surface). |
| link holder → server (read) | Anyone with the participant token can GET the grid; the query must expose only aggregate/answer data, never secrets (admin/cookie tokens). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering (stored XSS) | results.html grid cells, participant column headers + `title` attr, comments section (`internal/web/templates/results.html`) | high | mitigate | Render every participant-supplied value (display name, comment) exclusively via `{{.Field}}` template actions so html/template applies context-aware auto-escaping in both element and attribute context; introduce no raw-HTML wrapper type and no hand-built HTML strings. Enforced by the negative grep gate in both tasks' `<verify>` and by the markup-escaping unit test in Task 2. Continues Phase 2's T-02-04 posture. |
| T-03-02 | Information disclosure | `ResponsesByPollID` query + `buildResultsGridView` view-model (`internal/store/results.go`, `internal/web/server.go`) | medium | mitigate | The store query selects only `display_name`, `slot_id`, `answer`, `comment`; the view-model exposes only DisplayName/Answer/Comment/counts — never `cookie_token`, `admin_token`, or `participant_token`. This same view-model is what Plan 03-02 reuses for the admin route, guaranteeing no extra data leaks there. |
| T-03-03 | Denial of Service | `ResponsesByPollID` (unbounded result set) | low | accept | v1 is a self-hosted single-instance tool for small groups (per PROJECT.md); no per-poll participant cap is enforced. Two indexed SELECTs over a small table are acceptable; revisit only if hosted/multi-tenant scope is ever added (explicitly out of scope in REQUIREMENTS.md). |

No package-manager installs occur in this phase (pure Go stdlib + the already-present `modernc.org/sqlite`); the package-legitimacy gate is not applicable.
</threat_model>
