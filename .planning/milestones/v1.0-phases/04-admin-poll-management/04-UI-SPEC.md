# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope covered by this contract:** the admin-only edit form (`GET/POST /poll/{ptoken}/admin/{atoken}/edit`)
— title/description/slot-list editing, the disabled poll-type toggle, the inline slot-removal
warning, and the danger-zone whole-poll-delete section — plus the new "Remove" response-deletion
control added to the existing results grid on the admin route
(`GET /poll/{ptoken}/admin/{atoken}`). No changes to the participant-facing voting page
(`02-UI-SPEC.md`) or the read-only results-grid layout itself (`03-UI-SPEC.md`) beyond the one
added admin-only control row. This is the final phase of v1 — no UI surface remains undesigned
after this document.

**Stack basis:** same Go backend, server-rendered HTML (`html/template`) + hand-rolled CSS/JS as
Phases 1-3 — confirmed via `ls`/`find`: still no `components.json`/Tailwind config, still one
stylesheet (`internal/web/static/style.css`) and one script per page pattern
(`create.js`/`vote.js`/`copy.js`). shadcn gate not applicable (not a React/Next.js/Vite stack).
This phase **extends** the existing stylesheet and reuses every token declared in
`01-UI-SPEC.md`/`02-UI-SPEC.md`/`03-UI-SPEC.md` verbatim — **zero new hex values**. It introduces
exactly one new component pattern (`.btn-danger`, a solid destructive button — see Color below)
and reuses everything else (`.card`, `.form-section`, `.field`, `.btn-remove`, `.banner-error`,
`.toggle-group`, `.results-table` and friends) unchanged.

| Token | Value | Usage in this phase |
|-------|-------|----------------------|
| xs | 4px | Gap between the "marked for removal" strike-through label and its "Undo" link |
| sm | 8px | Gap between stacked slot rows (unchanged from Phase 1); gap inside the danger-zone card between its heading, body text, and button |

## Color

Inherited verbatim from `01`/`02`/`03-UI-SPEC.md` — **zero new hex values this phase**:

| Role | Value | Usage in this phase |
|------|-------|----------------------|
| Dominant (60%) | `#F8FAFC` | Page background/canvas (unchanged) |
| Secondary (30%) | `#FFFFFF` | Edit-form card surface (unchanged `.card`) |
| Accent (10%) | `#2563EB` | Primary CTA ("Save changes"), focus rings — unchanged reservation from Phase 1 |
| Destructive | `#DC2626` | See expanded reservation below — **first phase to use this token on a real, irreversible destructive control** |

**Note on destructive-color escalation (per `04-CONTEXT.md`'s explicit callout):** `#DC2626` was
declared in `01-UI-SPEC.md` for the "Remove slot" pre-submit row action (instantly reversible —
re-add restores it, no confirmation needed) and reused in `02`/`03-UI-SPEC.md` purely as the "No"
answer's semantic color (not a destructive control). This phase is the first to attach `#DC2626`
to controls that cause **real, irreversible data loss**: deleting a participant's response and
deleting an entire poll. Reusing the identical hex value is correct (one destructive token, per
the 60/30/10 + one-destructive-color contract) — but reusing the *identical visual treatment* as
the low-stakes "Remove slot" button would under-communicate the stakes of "delete everything."
Resolution (Claude's Discretion, flagged as the one open call in this contract — see return
summary): **two visual weights of the same destructive color**, both native-`confirm()`-gated
per `04-CONTEXT.md`:

| Control | Style | Weight | Used for |
|---------|-------|--------|----------|
| `.btn-remove` (existing, unchanged) | outline — `#DC2626` text/border on white | medium | "Remove slot" in the edit form (parity with Phase 1's creation form); "Remove" response-deletion button in the results grid |
| `.btn-danger` (**new this phase**, no new hex) | solid — `#FFFFFF` text on `#DC2626` background | heaviest | "Delete poll" only, inside the danger-zone card |

This is the smallest possible visual escalation (a background-fill inversion of an already-declared
color, not a new token) reserved for the single highest-stakes action in the entire app (cascading
deletion of the poll, all its slots, all participants, and all responses).

Danger-zone card treatment (new use of an already-established pattern, no new hex): background
`#FEF2F2` + `1px solid #DC2626` border — the exact tint/border pairing `.banner-error` already
uses in `02-UI-SPEC.md`, applied here to a persistent section rather than a transient validation
banner.

Disabled poll-type toggle (edit form, per `04-CONTEXT.md` — "shown... but disabled/read-only, not
hidden"): reuses `.toggle-group`/`.toggle-option` unchanged, with `opacity: 0.6` and
`cursor: not-allowed` added — a modifier on an existing pattern, not a new color or component.

Neutral text/border colors (unchanged, not part of the 60/30/10 split): body text `#1E293B`,
secondary/helper text `#64748B`, borders `#E2E8F0`.

## Visual Hierarchy

**Edit page**, top to bottom, in order of visual weight:

1. **Page title** ("Edit poll", `.display`, 28px/600) — unchanged role from prior phases
2. **Edit form** (title, description, organizer name, disabled poll-type toggle, slot list) —
   identical visual weight/order to Phase 1's creation form, since it is the same markup pattern
3. **Slot-removal aggregate warning** (only rendered when ≥1 slot is marked for removal) —
   interrupts the flow between the slot list and the submit button, deliberately placed where the
   admin cannot miss it before saving
4. **"Save changes" primary CTA** — accent-colored, same role as every prior primary CTA
5. **Danger zone** — always last on the page, visually separated by `xl` (32px) spacing and its
   own tinted card, so it reads as a distinct, deliberately-sought-out zone rather than an
   accidental click target near the main form's submit button

**Results/admin page** (extends Phase 3's hierarchy — items 1-5 unchanged, this phase adds one row):

6. **Per-participant "Remove" control** — lowest visual weight in the grid (outline style,
   compact), placed directly under the participant name in the header area so it's discoverable
   but never competes with the tally/badge data that is the grid's primary content

## Admin Controls Structure (markup + interaction contract)

Not a standard template section, but required here (matching Phase 3's "Grid Structure"
precedent) because `04-CONTEXT.md` left exact implementation to Claude's Discretion while locking
visible behavior:

**Response-delete control (results/admin page):**
- A second row directly below the existing header row, inside `<thead>`: `<tr class="results-admin-row">`
  with an empty sticky-column cell, then one cell per participant column containing
  `<button type="button" class="btn-remove btn-remove-response" data-participant-id="{{.ID}}">Remove</button>`.
- Rendered **only** on the admin route (`/admin/{atoken}` template variant) — the participant
  route's results partial is unchanged from Phase 3.
- Rendered **only** when `.HasResponses` is true (Phase 3's existing flag) — when there are zero
  responses there is no participant column to attach a control to, so this row is naturally absent;
  no separate empty-state copy needed.
- On click: native `confirm()` per Copywriting Contract, then `POST /poll/{ptoken}/admin/{atoken}/responses/{participantID}/delete`, then reload/redirect back to the admin page so the grid recomputes tallies and the best-fit highlight from current DB state (falls out of Phase 3's existing "always recompute" design, per `04-CONTEXT.md`).

**Slot-removal warning + confirm gate (edit form):**
- Clicking "Remove slot" on a row with `ResponseCount == 0`: row is removed from the DOM
  immediately (unchanged Phase 1 behavior — reversible, no data loss).
- Clicking "Remove slot" on a row with `ResponseCount > 0`: the row is **not** removed from the
  DOM. Instead it toggles to a `.slot-row-marked` visual state — muted background
  (`var(--color-bg)`), the slot label struck through (`text-decoration: line-through`), the inline
  warning copy shown beneath it, and the "Remove slot" button replaced with an "Undo" link/button.
  A hidden form field (e.g. `data-marked-for-removal="true"`) tracks this row's intent for submit.
- Once ≥1 row is marked, the aggregate warning banner (`.banner-error`-style tint, reusing the
  existing destructive tint/border pair) renders above the submit button with a required
  checkbox; "Save changes" (`disabled` attribute) only becomes clickable once the checkbox is
  checked. Unchecking it re-disables the button (live, client-side).
- Server-side mirrors this gate: a POST that includes marked-for-removal slots with existing
  responses but no confirmation flag is rejected with the "Confirm you understand..." banner
  error (defense in depth, matching every prior phase's client+server validation pattern).

**Danger zone (edit page, bottom of page):**
- `<div class="card danger-zone">` — new modifier class on the existing `.card` component:
  background `#FEF2F2`, border `1px solid var(--color-destructive)` (see Color section).
- Contains: `.heading` "Danger zone" (colored `var(--color-destructive)`), body copy, then
  `<button type="button" class="btn-danger">Delete poll</button>`.
- On click: native `confirm()` per Copywriting Contract, then
  `POST /poll/{ptoken}/admin/{atoken}/delete`; on success the browser is redirected to a URL that
  now 404s (reusing Phase 2's `notfound.html` — no distinct "deleted" message, per `04-CONTEXT.md`).

Applicable state considerations resolved: 10 covered, 2 backstop, 0 unresolved, 3 dismissed.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| populated | edit form (title/description/slots pre-filled from existing poll) | ✅ covered | Form always renders pre-filled with the current poll's data — same markup pattern as Phase 1's creation form, just with initial values instead of blanks. |
| partial | edit form slot list (some rows edited, some marked for removal, some untouched) | ✅ covered | Marked-for-removal rows render in a distinct muted/strikethrough state (`.slot-row-marked`) with an "Undo" affordance; untouched/edited rows render exactly as Phase 1's slot rows — see Admin Controls Structure above. |
| error | edit form — field validation | ✅ covered | Reuses the shared banner "Check the highlighted fields and try again." plus inline per-field messages, unchanged from Phase 1. |
| error | edit form — save attempted without confirming slot removal | ✅ covered | Client-side disabled-button gate plus server-side banner "Confirm you understand response data will be deleted before saving." — see Copywriting Contract. |
| loading | edit form (submit) | 🧪 backstop | "Save changes" disables and label changes to "Saving…" on click, reusing the existing submit-guard pattern from `create.js`; executor must verify this actually blocks a second POST, not just a visual state change (same bar as Phase 1/2's identical backstop). |
| empty | results/admin page — "Remove" response control with zero responses | ✅ covered | The admin-controls header row is simply absent when `.HasResponses` is false — there is no participant column to attach a "Remove" button to, so no separate empty-state message is needed (falls out of Phase 3's existing zero-response rendering). |
| interactive-control | results/admin page — "Remove" response-deletion button | ✅ covered | Native `confirm()` dialog per Copywriting Contract; on confirm, POSTs to the delete-response route and the grid recomputes on next render (no client-side tally math needed). |
| interactive-control | edit page — "Delete poll" button | ✅ covered | Native `confirm()` dialog with poll title + response count per `04-CONTEXT.md`; on confirm, POSTs to the delete-poll route. |
| loading | results/admin page — "Remove" / "Delete poll" actions | 🧪 backstop | Both actions are single-shot POSTs with no visible in-flight state declared beyond the browser's native navigation; executor must verify a double-click (e.g. double-confirming the native dialog somehow, or a slow network) cannot issue two deletes, not just that the route is idempotent in theory. |
| overflow | edit page — danger-zone confirm() dialog text with a very long poll title | dismissed | The dialog is a native browser `confirm()`, not styled HTML — the browser controls its own text wrapping/truncation; no CSS or layout contract applies here. |
| long-text | delete-poll / remove-response confirm() dialog copy | dismissed | Same reason as above — native dialog chrome, outside this app's styling contract. |
| zero-one-many | delete-poll confirm() dialog — response count | ✅ covered | Copy uses "{{.ResponseCount}} response(s)" — the parenthetical-s convention already used elsewhere in this app's copy (e.g. Phase 1's slot counter) rather than a full singular/plural branch, kept consistent across the codebase. |
| long-text | participant name in the "Remove" response button's `aria-label` | dismissed | The visible button label is always the fixed word "Remove" — only the `aria-label` embeds the (already 100-char-capped, per Phase 2) display name, and screen readers handle long strings natively; no visual truncation concern exists since the name is never rendered as visible button text. |
| zero-one-many | edit form slot-removal aggregate warning (1 slot vs. many marked for removal) | ✅ covered | Copy uses "{{.SlotCount}} slot(s)" / "{{.ResponseCount}} response(s)" — same parenthetical-s convention, avoids a conditional-copy branch while staying grammatically acceptable for both counts. |
