# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope covered by this contract:** the participant-facing voting page — display-name entry, a
Yes/No/Maybe pill-button group per slot, an optional overall comment, submit/resubmit, the
post-submit confirmation banner, and the invalid-link 404 page. Results grid (Phase 3) and admin
editing (Phase 4) have no UI surface here.

**Stack basis:** same Go backend, server-rendered HTML (`html/template`) + hand-rolled CSS/JS as
Phase 1 — no framework or dependency change in this phase (confirmed via `ls`/`find`: no
`components.json`/Tailwind config exist). This phase **extends** `internal/web/static/style.css`
in place rather than starting a new stylesheet, and reuses the tokens declared in
`01-UI-SPEC.md` rather than re-deriving them, per `02-CONTEXT.md`'s explicit instruction.

## Color

Inherited verbatim from `01-UI-SPEC.md`:

| Role | Value | Usage in this phase |
|------|-------|----------------------|
| Dominant (60%) | `#F8FAFC` | Page background/canvas |
| Secondary (30%) | `#FFFFFF` | Form card surface, each slot row's background |
| Accent (10%) | `#2563EB` | See reserved list below |
| Destructive | `#DC2626` | Not applicable this phase — see note below |

Accent (`#2563EB`) reserved for, in this phase's scope:
- Primary CTA button ("Save my response")
- Focus ring on all form inputs (`outline: 2px solid #2563EB`) — display-name field, comment
  textarea, and each pill-group segment
- The confirmation banner's border/accent treatment (reusing the existing `#EFF6FF` tint +
  `#2563EB` border combination already established for `.link-box-secret` in Phase 1 — no new
  hex value introduced)

**Decision (user override, superseding the initial single-accent draft):** each Yes/No/Maybe
pill gets its own selected-state color — the common Doodle/Rallly convention — so a slot's overall
sentiment is scannable at a glance across many rows without reading every label:

| Answer | Selected background | Selected text/icon | Rationale |
|--------|---------------------|---------------------|-----------|
| Yes | `#16A34A` (new token — green-600) | `#FFFFFF` | Positive convention |
| No | `#DC2626` (existing destructive token, reused) | `#FFFFFF` | Negative convention; reuses the token already declared for destructive actions rather than inventing a second red |
| Maybe | `#64748B` (existing secondary-text token, reused) | `#FFFFFF` | Neutral convention; reuses the existing muted-gray token rather than inventing a new neutral |

This deliberately expands the phase's color budget beyond the "one accent + one destructive"
cap Phase 1 established, because the researcher's single-accent draft was flagged and the user
explicitly chose the tri-color scheme. `#16A34A` is the one net-new hex value introduced this
phase; `#DC2626` and `#64748B` are reused from existing tokens, not new ones. Unselected pill
segments use the neutral surface/border colors below (no color until chosen).

Destructive (`#DC2626`) is now also used for the "No" pill's selected state (see table above) in
addition to its original reservation for actual destructive actions — there are still no
delete/remove controls on this page (deletion is Phase 4's `ADM-03`/`ADM-04` scope), so this is
purely a semantic-color reuse, not a new destructive control.

Neutral text/border colors (unchanged from Phase 1, not part of the 60/30/10 split): body text
`#1E293B`, secondary/helper text `#64748B` (also reused as the "Maybe" pill color per above),
borders `#E2E8F0`.

## Visual Hierarchy

Top to bottom, in order of visual weight:

1. **Page title** (the poll's title, `.display`, 28px/600) — primary focal point, same role as
   Phase 1's links page
2. **Display-name field** — secondary anchor; it's the first interactive element and establishes
   "who is answering" before any slot is shown
3. **Slot list (pill groups)** — the main body of the page; each row carries equal visual weight
   with no single slot emphasized over another (there's no "recommended slot" concept in this
   phase — that's Phase 3's best-availability highlight)
4. **Comment field** — tertiary, below the slot list; optional and de-emphasized relative to the
   required slot answers
5. **Primary CTA ("Save my response")** — final anchor, uses the accent color per the reservation
   list above

## Copywriting Contract

| Element | Copy |
|---------|------|
| Page title | The poll's title (`{{.Poll.Title}}`), rendered as `.display` — same pattern as the Phase 1 links page |
| Primary CTA | "Save my response" — a single, unbranching label used identically for first-time submit *and* for resubmitting an edited response (no "Submit" vs. "Update" split), because CONTEXT.md's data model is an upsert: the same action is semantically correct both times, and a single label avoids conditional template logic |
| Display-name field label | "Your name" |
| Display-name placeholder | "Jane Doe" |
| Comment field label | "Comment (optional)" |
| Comment placeholder | "Anything the group should know?" |
| Pill-group labels (per slot) | "Yes" / "No" / "Maybe" |
| Success banner (post-submit) | "Thanks! Your response has been saved." — verbatim per `02-CONTEXT.md`; shown above the still-editable form after a 303 redirect back to the same voting page |
| Error state — field validation | "Check the highlighted fields and try again." — reused verbatim from Phase 1's `#form-banner` pattern for consistency across the app's two form pages |
| Error state — display name blank | "Your name is required." — verbatim per `02-CONTEXT.md`, inline under the name field |
| Error state — slot missing an answer | "Choose Yes, No, or Maybe for this slot." — inline under the offending slot row, shown only on submit attempt (not live-as-selecting), matching Phase 1's "don't nag while interacting" pattern for row-level errors |
| Error state — invalid/unknown poll link | "This poll link isn't valid. Double-check the link you were given." — verbatim per `02-CONTEXT.md`, shown as the entire content of a plain 404 page (no form, no nav) |
| Destructive confirmation | Not applicable this phase — no destructive actions exist in the voting flow |

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5).

Applicable state considerations resolved: 9 covered, 1 backstop, 0 unresolved, 1 dismissed.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | voting form (new participant, no prior response) | ✅ covered | Every pill group renders with no segment selected, display name and comment blank — the "nothing chosen yet" state is the normal first-visit state, not a special empty-state message. |
| populated | voting form (returning participant, cookie matches an existing response) | ✅ covered | Display name, comment, and each slot's previously chosen pill pre-fill from the matched response on GET, per `02-CONTEXT.md`'s revisit/pre-fill decision. |
| loading | voting form (submit) | 🧪 backstop | Submit button disables and label changes to "Saving…" on click, reusing Phase 1's `create.js` submit-guard pattern (see `internal/web/static/create.js`'s `submitted` flag); executor must verify this actually blocks a second POST, not just a visual state change. |
| error | voting form — blank display name | ✅ covered | Inline field error "Your name is required." plus the shared banner "Check the highlighted fields and try again." |
| error | voting form — slot with no answer selected | ✅ covered | Inline row-level error "Choose Yes, No, or Maybe for this slot." surfaced only on submit attempt, not while interacting with other rows. |
| error | voting page — invalid/unknown poll token | ✅ covered | Plain 404 page, copy "This poll link isn't valid. Double-check the link you were given." — no form rendered at all. |
| partial | voting form (some slots answered, others not, before submit) | ✅ covered | No per-row live validation while the participant is still working through the list; the "must answer every slot" rule is enforced only at submit time (see error row above), so mid-form state is never flagged as an error. |
| long-text | comment field | ✅ covered | Textarea capped at `maxlength="500"` (native HTML enforcement, matching Phase 1's title/description pattern) — no truncation of what's stored or displayed, wraps naturally. |
| long-text | display-name field | ✅ covered | Input capped at `maxlength="100"` (matches `organizer_name`'s Phase 1 limit) — same native enforcement, no custom truncation. |
| overflow | slot list (many slots on one voting page) | ✅ covered | No fixed-height scroll container — the pill-group list grows with the page, identical to Phase 1's slot-list overflow resolution; simplest and most mobile-friendly for VOTE-06. |
| zero-one-many | slot list (1 slot vs. many) | dismissed | Unlike Phase 1's creation form, this page has no add/remove interaction and thus no live counter to keep correct — the vertical list layout is identical whether there is 1 slot or many, so no counter copy is needed. |
