# User story (MVP)

**As an** organizer holding the secret admin link,
**I want to** edit my live poll's title, description, and slot list (adding, changing, or removing slots) with clear warnings before I destroy response data,
**so that** I can correct mistakes and adjust the poll after it has gone live without needing an account and without silently losing votes.

> Story derived directly from the ROADMAP Phase 4 Goal line (which is outcome-shaped but not in strict `As a / I want to / so that` form). No scope was invented — roles and wants are taken from the Goal and CONTEXT.md. Recorded here as a visible planning choice because this is an autonomous, unattended run (no checkpoint raised for grey-area framing).

<objective>
Deliver the complete poll-editing capability (ADM-02): an admin-only edit page at `GET/POST /poll/{ptoken}/admin/{atoken}/edit` that reuses the Phase 1 create-poll form structure, pre-filled from the live poll, letting the organizer change title/description/organizer-name and the slot list — adding, editing-in-place, and removing slots — with the destructive slot-removal path gated by an inline warning plus an explicit confirmation.

Purpose: Editing is the first of Phase 4's three admin capabilities and the phase's architectural tracer — it introduces the entire `/edit` route, the `edit.html` template, the `edit.js` script, and the `internal/store/admin.go` mutation layer that the deletion plans (04-02, 04-03) build directly on. It is also the first live exercise of Phase 2's `ON DELETE CASCADE` on `responses.slot_id` via a real admin action rather than only a schema-level guarantee.

Output: A working, tested edit route; new store mutation methods; the edit template + progressive-enhancement script + CSS, all reusing Phases 1-3 tokens.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser to /edit (GET/POST) | Untrusted request crosses here; the only authorization is possession of BOTH the participant and admin tokens in the URL path (no session, no cookie-based auth). |
| handler to store mutation | Slot/poll writes cross here; a wrong poll_id or slot_id scoping bug here causes cross-poll data loss. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Spoofing / Elevation | GET/POST /poll/{ptoken}/admin/{atoken}/edit | high | mitigate | Authorization is possession of the unguessable crypto/rand admin token (existing internal/token model); the state-changing edit routes are reachable ONLY under the /admin/{atoken}/ path — there is no admin-token-less edit route. |
| T-04-02 | Tampering / Elevation | handleEditForm/handleUpdatePoll | high | mitigate | Resolve via `PollByTokens(ptoken, atoken)` which requires BOTH tokens to match the SAME poll row; a stale/mismatched pair yields ErrNotFound (404). All mutations use the resolved poll.ID, never a client-supplied poll id. |
| T-04-03 | Tampering / Elevation | UpdatePollSlots | high | mitigate | Every slot UPDATE/DELETE is scoped `WHERE id=? AND poll_id=?` with the resolved poll.ID, so a slot id belonging to another poll cannot be edited or deleted; covered by TestAdmin_UpdatePollSlots_ScopedByPoll. |
| T-04-04 | Denial of Service / accidental data loss | slot removal | medium | mitigate | Server-side confirm gate rejects a destructive removal without `confirm_slot_removal`; client-side inline warning + required checkbox is the UX safety net (per the security contribution, the confirm UX is a safety net, not the authorization control). |

| T-04-08 | Denial of Service | POST /edit body | medium | mitigate | `http.MaxBytesReader(w, r.Body, maxFormBytes)` on the edit POST, mirroring handleCreatePoll's 413/400 handling. |
