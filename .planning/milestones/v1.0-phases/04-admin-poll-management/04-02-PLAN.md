# User story (MVP)

**As an** organizer viewing my poll's results via the secret admin link,
**I want to** remove a single participant's response directly from the results grid,
**so that** I can clean up a mistaken, duplicate, or spam response and have the tallies and best-slot highlight instantly reflect the correction — without a separate management screen or an account.

> Story derived from the ROADMAP Phase 4 Goal and CONTEXT.md's "Deletion UX" decisions. Recorded as a visible planning choice for this autonomous run.

<objective>
Deliver response deletion (ADM-03): a per-participant "Remove" control on the admin results grid that, after a native confirm() dialog, deletes that participant's response via a new POST route and re-renders the grid with recomputed tallies.

Purpose: This is the second of Phase 4's admin capabilities. It builds on Phase 3's shared results grid (buildResultsGridView / results.html) and Phase 4 Plan 01's admin mutation layer (internal/store/admin.go). Deleting a "participant's response" means deleting the participant row, which cascades (Phase 2 schema, ON DELETE CASCADE on responses.participant_id) to remove their response rows — matching the UI-SPEC's "Remove this column" behavior.

Output: A new store deletion method, a new POST delete-response route, the admin-only "Remove" grid row, its confirm() JS, and its CSS — all reusing existing tokens.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser to delete-response POST | Untrusted request; authorization is possession of both tokens in the URL path (no session/cookie auth). |
| path {participantID} to store delete | A client-controlled participant id crosses here; must be scoped to the resolved poll. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Spoofing / Elevation | POST .../responses/{participantID}/delete | high | mitigate | Reachable only under /admin/{atoken}/; authorization is possession of the unguessable admin token (existing token model). |
| T-04-02 | Tampering / Elevation | handleDeleteResponse | high | mitigate | PollByTokens requires BOTH tokens to match the same poll (404 otherwise); delete uses the resolved poll.ID. |
| T-04-03 | Tampering / Elevation | DeleteParticipant scope | high | mitigate | `DELETE FROM participants WHERE id=? AND poll_id=?` — a participant id from another poll deletes nothing; covered by TestAdmin_DeleteParticipant_ScopedByPoll. |
| T-04-04 | Denial of Service / accidental data loss | Remove control | medium | mitigate | Native confirm() dialog + no-op-on-missing store behavior (a repeated delete is harmless); confirm() is a UX safety net, not the authorization control. |
| T-04-06 | Information disclosure | resultsParticipant.ID in grid | low | mitigate | The rendered id is the participant's store id (needed for the delete URL), never the cookie_token; cookie_token is not exposed (Phase 3 invariant preserved). |
| T-04-09 | CSRF | delete-response POST | low | accept | Authorization is a secret token in the URL path, not an ambient cookie/session credential, so there is no ambient credential for a cross-site POST to ride; anyone who knows the admin URL already holds full admin control by design. Documented and accepted. |
</threat_model>
