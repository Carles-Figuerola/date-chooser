<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> POST /polls | Untrusted title/description/organizer/slot values, and an attacker-controllable number of slot rows, cross into the app |
| client validation -> server validation | Client-side JS affordances are advisory; the server is the authority and must independently reject invalid input |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-03 | Tampering | store.CreatePoll multi-slot insert | high | mitigate | Parameterized placeholders only for every field and slot; no string concatenation of user input into SQL (verified in Task 2 acceptance) |
| T-01-04 | Denial of service | POST /polls body / slot-row count | medium | mitigate | `http.MaxBytesReader` (~1 MiB) caps the request body before ParseForm; oversized-body test asserts no panic and no DB write. Per CONTEXT there is no hard slot maximum (soft ~50 UI hint only), so the row-count cap is intentionally soft - the body-size cap bounds the real DoS surface |
| T-01-07 | Cross-site scripting (Tampering) | create.html re-render of submitted values | high | mitigate | Error re-render uses Go `html/template` auto-escaping for all echoed-back user values (title/description/organizer/slots); no `template.HTML`/raw interpolation of user input |
| T-01-08 | Tampering | poll_type field | low | mitigate | Server validates `poll_type` against the allowed set {all_day, date_time}; DB `CHECK(poll_type IN ('all_day','date_time'))` is the backstop |

ASVS level 1, block-on `high`: T-01-03 and T-01-07 are the high items and are both mitigated with verifiable gates. No package-manager installs occur in this plan.
</threat_model>
