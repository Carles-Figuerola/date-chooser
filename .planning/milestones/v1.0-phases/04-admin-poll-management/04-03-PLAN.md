# User story (MVP)

**As an** organizer holding the secret admin link,
**I want to** permanently delete the entire poll — and everything in it — from a clearly-separated danger zone with a confirmation that names the poll and its response count,
**so that** I can retire a poll for good when it is no longer needed, without leaving stale data around and without an account.

> Story derived from the ROADMAP Phase 4 Goal and CONTEXT.md's "Deletion UX" / "Page Layout & Deletion Semantics" decisions. Recorded as a visible planning choice for this autonomous run.

<objective>
Deliver whole-poll deletion (ADM-04): a "Danger zone" section at the bottom of the edit page with a solid destructive "Delete poll" button that, after a native confirm() dialog naming the poll and its response count, deletes the poll via a new POST route and cascades to all slots, participants, and responses — after which both links serve the existing invalid-link 404.

Purpose: The final admin capability and the final requirement of v1. It extends the edit page (Plan 04-01) with the danger zone, adds the delete-poll route/handler, and adds the DeletePoll store method — the last exercise of Phase 2's cascade chain (this time from the polls table down through slots, participants, and responses).

Output: A new store deletion method, a new POST delete-poll route, the danger-zone markup + CSS (introducing the single new `.btn-danger` component), and the delete-poll confirm() JS in edit.js.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser to delete-poll POST | Untrusted request; authorization is possession of both tokens in the URL path (no session/cookie auth). |
| handler to DeletePoll | The single most destructive write in the app crosses here; must operate only on the poll resolved from both tokens. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Spoofing / Elevation | POST /poll/{ptoken}/admin/{atoken}/delete | high | mitigate | Reachable only under /admin/{atoken}/; authorization is possession of the unguessable admin token (existing token model). |
| T-04-02 | Tampering / Elevation | handleDeletePoll | high | mitigate | PollByTokens requires BOTH tokens to match the same poll (404 otherwise); DeletePoll is called with the resolved poll.ID only, never a client-supplied id. |
| T-04-04 | Denial of Service / catastrophic data loss | Delete poll button | high | mitigate | Native confirm() naming the poll + response count (proportionate friction per CONTEXT.md) + no-op-on-missing store behavior; the solid .btn-danger + separated danger zone communicate the stakes. confirm() is a UX safety net, not the authorization control. |
| T-04-07 | Repudiation / accidental loss | whole-poll delete | low | accept | No audit log or soft-delete in v1 (deletion is immediate/permanent by decision; a distinct "deleted" message and undo window are Deferred Ideas). Accepted for a small self-hosted tool. |
| T-04-09 | CSRF | delete-poll POST | low | accept | Authorization is a secret token in the URL path, not an ambient cookie/session credential; there is no ambient credential for a cross-site POST to ride, and anyone who knows the admin URL already holds full admin control by design. Documented and accepted. |
</threat_model>
