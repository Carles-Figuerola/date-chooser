# Walking Skeleton — Date Chooser

**Phase:** 1
**Generated:** 2026-08-24

## Capability Proven End-to-End

> One sentence: the smallest user-visible capability that exercises the full stack.

An organizer opens the create-poll page, submits the form with a title and one candidate slot, and is immediately redirected to a page showing a working participant link and a separate secret admin link — with the poll persisted in a SQLite file that survives a container restart, all served by the single Docker image.

## Architectural Decisions

These are the load-bearing choices later phases (voting, results grid, admin management) build on **without re-litigating**. Schema shape and token format are one-way-door decisions (flagged `reversibility=one-way` on the tracer task; recorded, not gated, because this is an autonomous run).

| Decision | Choice | Rationale |
|---|---|---|
| Language / runtime | Go 1.23, single static binary (`CGO_ENABLED=0`) | CONTEXT decision: Go single static binary over Python; static binary enables a `scratch`/distroless final image with no C toolchain |
| HTTP routing | stdlib `net/http` + Go 1.22+ `ServeMux` method/wildcard patterns (`GET /{$}`, `GET /poll/{ptoken}/admin/{atoken}`) | CONTEXT Claude's-Discretion: keep the binary dependency-light; Go 1.22 pattern routing removes any need for a third-party router |
| Templating | `html/template`, embedded via `//go:embed templates/*.html` | Server-rendered HTML per CONTEXT; embedding keeps everything in the one binary (no runtime asset path) |
| Data layer | SQLite via `modernc.org/sqlite` (pure Go), embedded `schema.sql`, idempotent `CREATE TABLE IF NOT EXISTS` on startup, `PRAGMA foreign_keys=ON` | CONTEXT decisions: pure-Go driver avoids CGO/cross-compilation; embedded idempotent schema instead of a migration framework for v1 |
| Schema (this phase) | `polls` + `slots` tables only; `participants` + `responses` deferred to Phase 2 (when voting exists to fill them) | Vertical slice — Phase 1 creates only what poll creation needs; the normalized 4-table model completes in Phase 2 additively |
| Tokens | `crypto/rand`, 16 bytes (128-bit) → `base64.RawURLEncoding`; `participant_token` and `admin_token` generated by two independent calls, stored in separate columns | CONTEXT decisions: cryptographically random URL-safe ~128-bit tokens; admin token NOT derivable from participant token |
| URL shape | Participant: `/poll/{participant_token}`; Admin: `/poll/{participant_token}/admin/{admin_token}` | CONTEXT decision (verbatim URL structure) |
| Post-create flow | `POST /polls` → 303 See Other → `GET /poll/{pt}/admin/{at}` (Post/Redirect/Get) renders the links page | Discretion choice: PRG prevents duplicate polls on refresh and reuses the admin route; the admin link living in the URL is inherent to the link-based access model |
| Config | Env vars only: `PORT` (default `8080`), `DB_PATH` (default `/data/datechooser.db`) | CONTEXT decision (verbatim) |
| Deployment | Multi-stage Dockerfile: `golang:1.23` build → `gcr.io/distroless/static-debian12:nonroot` final; `VOLUME ["/data"]`; `/data` created owned by uid 65532 so a fresh named volume inherits writable ownership | CONTEXT decision (multi-stage, scratch/distroless minimal image); nonroot chosen for security; `/data` ownership handled so OPS-03 fresh-volume start works out of the box |
| Directory layout | `cmd/server/main.go` entrypoint + `internal/{store,token,web}`; web assets embedded under `internal/web/{templates,static}` | Discretion choice: standard Go layout, embed requires assets to live under their package directory |

## Stack Touched in Phase 1

- [x] Project scaffold (Go module, `cmd/server` entrypoint, build via `go build ./...`)
- [x] Routing — real routes: `GET /{$}`, `POST /polls`, `GET /poll/{ptoken}/admin/{atoken}`, `GET /healthz`, `GET /static/`
- [x] Database — real read AND write: `CreatePoll` inserts a poll + slots (write); `PollByTokens` reads them back for the links page (read); `Ping` for `/healthz`
- [x] UI — interactive element wired to the backend: the poll-creation form POSTs and the browser lands on the rendered links page
- [x] Deployment — running in the single Docker image; documented local full-stack run: `DB_PATH=./dev.db PORT=8080 go run ./cmd/server`, and container run in Plan 01 Task 2

## Out of Scope (Deferred to Later Slices)

> Explicit so future phases do not re-litigate Phase 1's minimalism.

- Voting: no participant vote capture, no `participants`/`responses` tables yet (Phase 2)
- Results grid, tallies, best-slot highlight, comments display (Phase 3)
- Admin editing / deletion of polls or responses (Phase 4)
- Timezone handling, calendar export, notifications (v2, out of scope entirely)
- Rate limiting on link access (CONTEXT decision: token entropy is the only protection in v1)
- HTTPS enforcement / redirect (CONTEXT decision: operator's reverse proxy terminates TLS)
- Migration framework (idempotent embedded `schema.sql` only in v1)

## Subsequent Slice Plan

Each later phase adds one vertical slice on top of this skeleton without altering its architectural decisions:

- **Phase 2 — Voting End-to-End:** adds `participants` + `responses` tables (additive `CREATE TABLE IF NOT EXISTS`), a `GET /poll/{ptoken}` voting page, and a `POST /poll/{ptoken}/respond` handler; reuses the same store, templates, and token model.
- **Phase 3 — Results Grid:** adds a results view (slots × participants) rendered from the same store; no new architectural decisions.
- **Phase 4 — Admin Poll Management:** adds edit/delete handlers gated behind the existing `admin_token` route; reuses the admin URL established here.
