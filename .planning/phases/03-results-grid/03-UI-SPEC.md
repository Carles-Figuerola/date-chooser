# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope covered by this contract:** the results-grid section that renders below the existing
voting form on `GET /poll/{ptoken}` and identically on `GET /poll/{ptoken}/admin/{atoken}` — the
slots-by-participants grid with per-cell Yes/No/Maybe badges, per-slot tallies, the best-slot
highlight, and the comments list below the grid. No editing/deletion controls exist yet
(Phase 4/ADM-02..04). The vote form itself is unchanged from `02-UI-SPEC.md`.

**Stack basis:** same Go backend, server-rendered HTML (`html/template`) + hand-rolled CSS as
Phases 1-2 — confirmed via `ls`/`find`: no `components.json`/Tailwind config exist, `internal/web/static/style.css`
is the single stylesheet. This phase **extends** that stylesheet in place and reuses every token
declared in `01-UI-SPEC.md` and `02-UI-SPEC.md` verbatim (no shadcn gate — not a React/Next.js/Vite
stack). The one net-new visual element is the grid itself; no new color tokens are introduced —
`03-CONTEXT.md` explicitly requires reusing Phase 2's tri-color tokens and Phase 1's accent-tint
box treatment rather than inventing new ones.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — unchanged from Phases 1-2; shadcn gate not applicable (not a React/Next.js/Vite stack) |
| Preset | not applicable |
| Component library | none — hand-rolled semantic HTML (`<table>`), extending `internal/web/static/style.css` |
| Icon library | none — unchanged; the grid uses plain-text glyph characters (✓/✗/?) inside badges, not an icon library (see Color/Copywriting below) |
| Font | system font stack: `-apple-system, "Segoe UI", Roboto, Helvetica, Arial, sans-serif` — unchanged |

Rationale: greenfield tokens were established in Phase 1 and extended in Phase 2; `03-CONTEXT.md`
locks reuse of the tri-color tokens and the `#EFF6FF` accent-tint box treatment. This document adds
only the layout/markup contract for the grid — no new hex values, no new font sizes, no new weights.

**Layout note (Claude's Discretion per `03-CONTEXT.md`):** the vote form above keeps the existing
`.page` 640px max-width container. The results section breaks out of that container to its own
wrapper capped at **960px** max-width (still centered, same side padding), because a slots × participants
grid needs materially more horizontal room on desktop than a single-column form — capping it at 640px
would force horizontal scrolling even for 3-4 participants on a laptop screen, which defeats the
"see at a glance" goal in RES-01. On narrow/mobile viewports both sections behave identically
(full-width minus padding); the 960px cap only matters above that breakpoint.

## Spacing Scale

Declared values (inherited verbatim from `01-UI-SPEC.md` / `02-UI-SPEC.md` — must be multiples of 4):

| Token | Value | Usage in this phase |
|-------|-------|----------------------|
| xs | 4px | Gap between tally segments ("3 Yes · 1 No · 0 Maybe"), gap inside a grid badge |
| sm | 8px | Grid cell padding (all four sides), gap between grid section and comments section header |
| md | 16px | Gap between the vote-form card and the results section; gap between grid and comments list |
| lg | 24px | Results section / comments section internal padding (matches `.card`) |
| xl | 32px | Not used at the grid-element level; reserved for page-level rhythm (already applied by existing `.page`) |
| 2xl | 48px | Space above the "Results" section heading, same role as existing page-title spacing |
| 3xl | 64px | Not used this phase |

Exceptions:
- The 44px minimum tap-target floor from Phase 1/2 does **not** apply to grid data cells — cells
  are non-interactive display elements (badges, tallies, comments), not controls. It still applies
  to the vote form above, unchanged.
- Grid data cell minimum width: 48px (enough for the largest badge + padding without cramping).
- Sticky slot-label column minimum width: 168px (fits the longest existing slot-label format —
  a date + time range — without wrapping to more than 2 lines in the common case).

recombination of already-declared values, not a new size or weight, so it does not expand the
typography budget.

## Visual Hierarchy

Top to bottom, in order of visual weight (extends Phase 2's hierarchy; items 1-2 are unchanged):

1. **Page title** (poll title, `.display`, 28px/600) — unchanged
2. **Vote form** (unchanged from `02-UI-SPEC.md`) — renders first per `03-CONTEXT.md`'s explicit
   "vote form on top, results grid below" placement decision
3. **"Results" section heading** (`.heading`, 20px/600) — introduces the grid
4. **Results grid** — the main new focal point; the best-slot row(s) carry the highest weight
   within the grid via the tint + border + "Best fit" badge treatment; all other rows carry equal
   weight (no secondary emphasis tiers)
5. **"Comments" section heading + list** (only rendered if at least one non-empty comment exists)
   — tertiary, below the grid, lowest visual weight on the page

## Grid Structure (markup + interaction contract)

Not a standard template section, but required here because the grid is this phase's only new UI
element and `03-CONTEXT.md` left the exact implementation to Claude's Discretion while locking the
visible behavior:

- **Element:** `<table>` (semantic HTML — sortable/scannable data, not a CSS-grid layout), wrapped
  in a scroll container `<div class="results-scroll">` with `overflow-x: auto`.
- **Sticky column:** the first `<th>`/`<td>` column (slot label) gets `position: sticky; left: 0;
  background: var(--color-surface);` plus a 1px right border (`--color-border`) so it visually
  separates from scrolling content and never shows a transparent seam.
- **Header row:** background `--color-surface`, bottom border `1px solid var(--color-border)`,
  participant name in Label style (14px/600).
- **Header row long-name handling:** each participant header cell has `max-width: 140px`,
  `overflow: hidden`, `text-overflow: ellipsis`, `white-space: nowrap`, plus a native `title`
  attribute carrying the full name — display names are already capped at 100 chars (Phase 2), so
  this only affects genuinely long names in a dense grid; no JS tooltip needed.
- **Data cell content:** a single glyph character — **"✓" / "✗" / "?"** (Yes/No/Maybe) — in the
  tri-color badge styled `inline-flex`, `min-width: 28px`, `min-height: 28px`, `border-radius: 6px`
  (matches the app's existing 6px radius convention, not circular), 14px/600 white text, centered.
  Rationale for glyph characters over an icon library: `03-CONTEXT.md` already rejected full-word
  labels as too wide; a true icon library (SVG sprite set etc.) would introduce a dependency Phase
  1 explicitly avoided ("no icon library... no external icon dependency"). `✓`/`✗`/`?` are plain
  Unicode text characters — same "no new dependency" property as the letter option, but more
  scannable at a glance across a dense grid than Y/N/M (user-confirmed choice, overriding the
  researcher's letter-badge draft).
- **Missing-cell fallback:** plain "—" character, no badge chrome (see Color above).
- **Slot-label cell (sticky column) content:** slot label (Label style) on the first line, then the
  tally line ("N Yes · N No · N Maybe", 14px/400 muted) on the second line, then the "Best fit"
  badge (if this row is a top-ranked slot) on a third line.
- **Best-slot row:** `background: #EFF6FF;` on every cell in the row, `border-left: 3px solid
  #2563EB;` on the sticky column only (avoids a heavy border running through every data cell), plus
  the "Best fit" text badge described above. Applied to every tied top-rank row per `03-CONTEXT.md`
  (never arbitrarily pick one).
- **Zero-response state:** grid still renders (rows for every slot, columns for zero participants
  collapses to just the sticky label column), no highlight logic runs, and a single muted note
  line ("No responses yet.") replaces where tallies/badges would be — per `03-CONTEXT.md`.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Results section heading | "Results" |
| Comments section heading | "Comments" (entire section, heading included, omitted when there are zero non-empty comments) |
| Comment line format | "**{name}**: {comment}" — one line per participant with a non-empty comment, name in Label style, comment in Body style |

| Grid badge — No | "✗" (white text on `#DC2626`) |
| Grid badge — Maybe | "?" (white text on `#64748B`) |
| Missing-cell fallback | "—" (em dash, muted gray, no badge background) |
| Best-slot badge | "Best fit" |
| Zero-response note | "No responses yet." |
| Tally format (per slot) | "{yesCount} Yes · {noCount} No · {maybeCount} Maybe" |
| Primary CTA | Not applicable this phase — the page's only CTA remains the vote form's existing "Save my response" (unchanged from `02-UI-SPEC.md`); the results grid itself is read-only with no action button |
| Empty state | See "Zero-response note" above — this is the grid's only empty state, and it's a note, not a blocking screen (the vote form above is always interactive regardless of response count) |
| Error state | Not applicable — this phase adds no new form or submission; store/query failures fall back to the existing generic error handling already in place for the page (no new error copy introduced) |
| Destructive confirmation | Not applicable — no destructive actions in this phase's scope (deletion arrives in Phase 4 / ADM-03, ADM-04) |

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
> Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers
> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

Applicable state considerations resolved: 9 covered, 2 backstop, 0 unresolved, 1 dismissed.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | results grid (zero participants/responses) | ✅ covered | Grid renders with slot rows and zero data columns; highlight logic does not run; muted "No responses yet." note replaces tallies/badges — see Copywriting Contract. |
| populated | results grid (N participants, all slots answered) | ✅ covered | Standard case: one badge per slot × participant cell, tallies computed and shown per slot, top-rank row(s) highlighted. |
| partial | results grid (a cell has no response) | ✅ covered | Renders as "—" muted text fallback, not a styled badge, per `03-CONTEXT.md`'s "honest data fallback, not a designed empty state" decision; this should not normally occur since Phase 2 requires every slot answered before submit. |
| overflow | results grid (many participant columns, narrow viewport) | 🧪 backstop | Horizontal scroll container with the slot-label column pinned via `position: sticky; left: 0`; executor must verify the sticky column actually stays visible while scrolling at a ~360px viewport width, not just declare the CSS rule (same verification bar as Phase 1's link-wrapping backstop). |
| long-text | results grid (participant display name in column header) | 🧪 backstop | Ellipsis-truncated at 140px with a native `title` attribute holding the full name; executor must verify truncation actually triggers for a long name and that the full name is still recoverable (hover/long-press), not just that the CSS property is present. |
| long-text | comments list (comment body) | ✅ covered | Full text shown, no truncation — comments are already capped at 500 chars from Phase 2, wraps naturally via Body style, matching `03-CONTEXT.md`'s explicit "no truncation" decision. |
| empty | comments section (zero non-empty comments across all responses) | ✅ covered | Entire section (heading included) is omitted — no empty "Comments" heading shown, per `03-CONTEXT.md`. |
| zero-one-many | results grid (1 participant vs. many participants) | ✅ covered | Grid markup is identical regardless of column count — 1 column renders the same table structure as N columns, just narrower; no special-case layout needed. |
| loading | results grid | dismissed | Server-rendered on the same request as the vote form — no async fetch exists to show a loading state for. |
| error | results grid (best-slot ranking with a tie) | ✅ covered | All tied top-rank slots are highlighted, never an arbitrary single pick, per `03-CONTEXT.md`. |
| error | results grid (store/query failure) | ⚠ unresolved | No new error UI specified this phase; planner should treat "falls back to existing generic error handling" as an assumption to confirm during planning, since no prior phase's UI-SPEC defined a generic 500 page contract to point to. |
